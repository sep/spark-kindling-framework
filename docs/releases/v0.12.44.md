# v0.12.44 — Incremental Delta inputs, and temporal strata that match their rules

Two Lakeflow lowering changes, plus a config-bridge fix and a name-resolution defect found during review.

Package versions:

- Runtime, CLI, SDK: **0.12.44**.
- Databricks extension: **0.1.14**, requiring runtime **0.12.39+** and SDP **0.3.2+**.
- SDP extension: **0.3.4** (first change since 0.12.40).
- Temporal extension: **0.2.7** (unchanged since 0.12.43).

## Incremental reads of external Delta inputs

A normal Kindling pipe whose driving input is an ordinary Delta table — one written by a separate ingestion pipeline, not by a streaming provider — can now be read incrementally on Databricks Lakeflow, opting in per pipe:

```yaml
datapipes:
  silver.device_telemetry:
    engine:
      databricks_sdp:
        streaming_inputs: ["bronze.device_telemetry"]
```

The output is then declared as a streaming table plus one append flow, the named input is read with `spark.readStream.table(...)`, and every other input stays a batch read, so reference-table joins remain stream-static. Expectations, table properties, partitioning, clustering and the deferred `schema` forwarding behave exactly as they already did for provider-owned streaming sources; both shapes reach the same emission path.

Most of this already existed. `_build_dataset_function(stream_driving_inputs=True)` has always streamed driving EXTERNAL inputs and kept the rest batch; what never happened was *selecting* that emission for an ordinary Delta table, because only a provider implementing `DeclarableStreamingSource` (Event Hubs) set the field that routes there. This release adds the opt-in that does, not the plumbing beneath it.

**The opt-in is never inferred.** An incremental read makes a pipe append-only with no reprocessing of revised rows — a semantic change the application owns, not something the adapter should decide for every Delta entity. A Delta input not named here is untouched.

It is adapter-tier: `engine="sdp"` reports `capability_not_supported`. Unsupported shapes fail at declaration time with `streaming_input_not_an_input`, `streaming_input_not_driving`, `streaming_inputs_partial`, `multiple_streaming_inputs`, `streaming_input_not_delta`, `streaming_input_internal`, `streaming_input_provider_owned`, or the existing `streaming_dataset_type_conflict`. `streaming_inputs_partial` is the one worth knowing: the append flow streams whatever `driving_entity_ids` selects, so a partial opt-in would silently stream an input nobody opted in — the sets must match.

## Streamed external reads now resolve physical table names

Found in review, and older than the feature above. The default streamed-external resolver read `spark.readStream.table(<logical entity id>)` while the batch resolver resolved through `EntityNameMapper`. Any entity using `provider.table_catalog`, `provider.table_schema`, `provider.table_name`, or a non-default naming strategy would therefore stream from the wrong name or fail to resolve outright.

This was already live on the **AUTO CDC change-feed path**, which uses the same route — not only on the new opt-in. It stayed invisible because that path's two streaming tests overrode the batch resolver but not the streaming one, so both sides agreed on raw entity ids and nothing compared them against a real name mapper. Both resolvers now share one `_external_table_name` helper, the test overrides are symmetric, and physical-name resolution has its own test against the real defaults.

If you declare an SCD change-feed pipe whose driving input carries `provider.table_*` tags, this is a behavioral fix: that flow was reading the wrong name before.

## Temporal strata match their rule depth

`kindling.temporal.max_generations` is a ceiling — the lowering rejects a rule set reaching past it — but the emitted topology was built from it directly. A single-condition app at the default of 10 therefore declared eleven strata, nine permanently empty, and not inert: each empty stratum is a dataset with a flow that reads the base stratum and discards every row.

The constraint that produced this is real but narrower than the old code assumed. Emission and `validate()`'s name reservation must produce identical dataset names, and reservation runs with no Spark session, so the count could only ever come from configuration. That does not bind registry-declared conditions: they are code, readable in-process from the condition registry by both paths. A chain whose conditions all come from `DataConditions.register` now declares exactly the depth its rules reach — `__g0` and `__g1` for a single-generation app.

A chain with any table-sourced condition engine keeps the ceiling as its topology, because rule rows change between updates and reservation cannot read their depth. Any failure to resolve the depth falls back to the ceiling, so both paths degrade together and a declaration can never fail on this.

Shrinking a registry chain's depth leaves the highest `__g*` dataset behind, no longer updated — a deploy-time event; drop the stale table once.

## `kindling.temporal.max_generations` is now bridged

The declaration path reads this key, but it was absent from the restricted-runtime point-lookup list. On serverless and shared-access clusters, where every configuration enumeration surface is blocked, setting it as pipeline configuration was silently ignored and the ceiling stayed at its default — precisely the failure that list's own comment warns about. If you tried tuning it as pipeline config before, it did nothing.

## Upgrading

Nothing changes for an existing pipe: the opt-in is absent by default, and chains with table-sourced conditions keep their current topology. ADX-snapshot/SCD2 pipes and the temporal chain's own batch processing are untouched. The one behavioral change to check for is the streamed-name fix above, on an AUTO CDC change-feed pipe whose driving input carries `provider.table_*` tags.

Validation: 2,983 unit tests passed (2 skipped); black, isort and flake8 clean. 20 new tests cover the opt-in and its rejections, emission and reservation agreeing on the collapsed topology, a degraded registry lookup falling back rather than raising, and physical-name resolution on the streamed path. This is a fast-track release: release wheel builds and smoke tests remain enabled; cloud system tests are skipped.

Real-workspace acceptance of an opted-in Delta streaming pipe is outstanding, as is the batch-mode acceptance carried over from v0.12.41.
