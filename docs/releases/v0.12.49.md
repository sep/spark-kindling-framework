# v0.12.49 — `kindling bundle build`, settings by convention, Databricks CLI in the devcontainer

This release adds the missing bridge between a Kindling project and a Databricks bundle, makes settings discovery a convention everywhere (Lakeflow pipelines receive their settings inline; local apps and the CLI name directories instead of files), fixes a core bug that made the declaration-only platform fallback crash on serverless, and ships the Databricks CLI in both devcontainer images.

Package versions:

- Runtime, CLI, SDK: **0.12.49**.
- Databricks extension: **0.2.0** (from 0.1.14; breaking on the Lakeflow settings surface, see below).
- SDP extension: **0.3.4** (unchanged).
- Cosmos DB extension: **0.2.0** (unchanged).
- Temporal extension: **0.2.7** (unchanged).

## `kindling bundle build`

`kindling bundle build` precompiles a project into the files `databricks bundle validate/deploy/run` need. It is Spark-free and imports no app code. Inputs are the project's settings overlays, found by convention (`config/settings.yaml`, `settings.databricks.yaml`, `workspace_<id>.yaml`, `settings.<env>.yaml`, then the app's `settings*.yaml` under `data-apps/` or `apps/`), plus typed deployment inputs from options or `KINDLING_BUNDLE_*` variables (options win; runtime settings are never consulted). Output is a disposable directory, `dist/bundles/databricks` by default: `databricks.yml`, one `resources/<key>.pipeline.yml` per pipeline (serverless Lakeflow pipeline running the generic `declare_from_pipeline_config()` source), the source file, staged wheels, and a provenance `manifest.json` with the SHA-256 of every input. Identical inputs give identical output; there are no timestamps. The output directory is only replaced when it is empty, was written by the generator, or `--force` is passed, and it may never overlap the project's config or app directories.

`--app-options-json` sets per-app catalog, schema, continuous mode and pipe subsets, or splits an app into several pipelines (`{"orders": {"pipelines": {"bronze": {...}, "silver": {...}}}}`). `--wheel` stages local wheels that `databricks bundle deploy` uploads under the bundle's workspace root and installs into the pipeline environment in the order given; list them dependency-first (core, SDP extension, Databricks extension, app), because serverless installs them one at a time and Kindling packages are not on PyPI. The Databricks CLI keeps validate, deploy and run; the command prints the next steps. `examples/lakeflow-telemetry` is now a project plus generated `bundle/` output pinned by a drift test.

## Lakeflow settings travel inline; file lists are gone (breaking)

Each generated pipeline resource carries its app's merged settings tree as `kindling.lakeflow.settings_json`. The Lakeflow selector injects the top-level sections (`kindling`, `dataentities`, `datapipes`, `*-bytag`, ...) literally, so dotted entity ids and tag keys are never split into paths; a flat pipeline key naming the same leaf still wins as a just-in-time override; an inline `kindling.platform.environment` feeds early platform selection; and the key is point-looked-up on serverless without being named in `kindling.lakeflow.config_keys`. The deployed pipeline reads no settings files from the workspace or a volume.

Settings-file lists are no longer a Lakeflow concept: the selector stops reading `spark.kindling.bootstrap.config_files` (and the long-removed `kindling.lakeflow.config_files` alias). A pipeline still setting either gets a warning and the value is dropped, never read. Migrate by generating the bundle, or by putting the merged settings in `kindling.lakeflow.settings_json` by hand for a small pipeline. The runtime's own artifacts-storage discovery is unchanged.

Verified end to end on a real serverless pipeline: `tests/system/extensions/databricks/test_bundle_build_platform.py` builds this checkout's wheels, generates a bundle, deploys and runs it through the Databricks CLI, checks table properties and expectations driven by the inline configuration via SQL, and destroys it.

## Settings discovery by convention: `config_dir` / `app_dir`; `config_files` deprecated

Explicit settings-file lists stop being a user-facing concept. Callers name where settings live and bootstrap finds which files by the documented convention, from one hierarchy table (`settings_hierarchy`) shared with the artifacts-storage download so the two cannot drift: `settings.yaml`, `settings.<platform>.yaml`, `workspace_<id>.yaml`, `settings.<env>.yaml`, then the app's base/platform/env overlays, with the documented legacy names (`platform_<p>.yaml`, `env_<e>.yaml`, `app.<p>.yaml`, `app.<e>.yaml`) honoured when the canonical file is absent.

```python
kindling.initialize(config={
    "environment": "dev",
    "config_dir": "/path/to/config",     # shared overlays
    "app_dir": "/path/to/apps/orders",   # the app's own overlays
})
```

Local directories layer on top of anything discovered in artifacts storage. A `kindling.platform.environment` in a convention-found file drives early platform selection as it did for explicit files, and the directories are part of the re-initialization identity. Bootstrap `config_files` still loads (last) but warns and names the replacement. The CLI's own bootstrap, `kindling app run`, the local runner (`--config-dir` replaces repeated `--config <file>`), the scaffolded component/integration test templates and the local fixture project no longer build file lists; `--config` on the CLI keeps its directory meaning and now applies the shared overlays *in addition to* the app's own. Proposal: `docs/proposals/settings_discovery_by_convention.md`.

## Fixed: declaration-only platform fallback crashed instead of falling back

When the Databricks platform service cannot be constructed inside a serverless pipeline (no detectable workspace id), bootstrap falls back to the standalone service for declaration-time operations. The fallback's warning used printf-style arguments that `SparkLogger.warning` does not accept, so every such pipeline failed with a `TypeError` that hid the original error. The message is formatted first now. Found by the end-to-end run above.

## Devcontainer: Databricks CLI

Both the repository's `.devcontainer/Dockerfile` and the published domain image (`.github/Dockerfile.devcontainer`) install the Databricks CLI at a pinned `DATABRICKS_CLI_VERSION` (1.18.0), downloaded from the GitHub release for the container architecture and verified against the release checksums. Rebuild the container or pull the republished image to pick it up. The published-image build also no longer passes the GitHub release JSON through the shell's `echo` when resolving the latest CLI/SDK wheels; the 0.12.48 release body had broken that parse.
