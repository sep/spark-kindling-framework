# v0.12.41 — Configurable temporal-chain execution mode for Lakeflow

Databricks Lakeflow temporal chains can now lower their event strata as batch materialized views instead of streaming tables with append flows. `kindling.lakeflow.temporal_mode: batch` makes each base-event transform an ordinary batch Spark query, so ordered analytic windows — `row_number`, `lag`, unbounded forward fill — become declarable on the Lakeflow path. The default is unchanged.

Package versions:

- Runtime, CLI, SDK: **0.12.41**.
- Databricks extension: **0.1.11**, requiring runtime **0.12.39+** and SDP **0.3.2+**.
- SDP extension: **0.3.2** (unchanged).

Batch mode converts `<events>__g0..gK` to one materialized view per stratum with `spark.table` reads. Everything from the episode snapshot downstream is unchanged in both modes — the snapshot already read the strata in batch — as are multi-source fan-in, external base-source resolution through `EntityNameMapper`, generated-name reservations, episode SCD2 history, and the runner engine's watermark behavior. A batch chain declares no `readStream` and no append flow; a chain with episodes still creates a streaming table for the snapshot-CDC target only, because that API requires one.

Batch strata carry batch-query semantics rather than append-only history: a refresh can revise or remove previously produced events, and late arrivals can change window results across a subject partition. Retain the source history your computation needs, use stable event identity with deterministic window ordering, and treat a mode change as a dataset-type change for newly provisioned outputs — nothing is dropped or reset automatically.

The canonical `spark.kindling.lakeflow.temporal_mode` bundle key is point-looked-up by the Lakeflow selector, so it also resolves on serverless and shared-access runtimes that cannot enumerate Spark configuration. An invalid value fails the declaration before any Lakeflow object is created, and the setting is inert when no temporal chain-events pipe is selected.

See the [Databricks extension documentation](../../packages/extensions/kindling_ext_databricks/README.md#temporal-chain-execution-mode) for the topology table and semantics, the [configuration reference](../reference/config_reference.md) for the key, and [the proposal](../proposals/temporal_lakeflow_execution_mode.md) for the design record and its review.

Validation: 2,947 unit tests passed (2 skipped) and 151 integration tests passed, including five new real-Spark tests that evaluate the emitted query functions, assert `isStreaming` is false, and force execution of a `row_number` window. One pre-existing integration failure (`test_sdp_mode.py::test_dataset_function_reads_real_table_and_transforms`) reproduces identically at v0.12.40 and is unrelated. This is a fast-track release: release wheel builds and smoke tests remain enabled; cloud system tests are skipped.

Real-workspace acceptance is still outstanding. Batch-mode snapshot CDC over materialized-view strata, and materialized-view refresh ordering across multiple updates with a late correction, require the extended Lakeflow temporal system test on a live workspace before batch mode should be advertised as platform-validated. Making a same-pipeline producer resolve to its pipeline-local dataset name — so internal base sources form real dependency edges — remains a documented follow-up affecting both modes.
