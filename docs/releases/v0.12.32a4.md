# Release Notes - v0.12.32a4

Alpha release. Fixes a batch of uv-workspace and Databricks deploy issues
found while onboarding a downstream domain project onto `0.12.32a2`/`a3`.

## Fixed

- **`kindling env update` left a nested project's own Kindling pin
  untouched, breaking the next `uv sync`/`uv add` in the workspace.** It
  only rewrote the version at `--project`'s own pyproject.toml, never a
  nested workspace member's own independent pin, so the root and a member
  could end up on two different releases -- `uv`'s resolver correctly
  refused to lock the result ("conflicting URLs for package
  spark-kindling") on the very next sync. `env update` now also updates
  every other project under `--project` that declares its own Kindling
  dependency.
- **Remote app runs could silently install a very old, wrong Kindling
  wheel.** `DataAppManager._select_best_wheel` sorted candidates ascending
  by `(priority, version)` and returned index `0` -- the *lowest* version
  within the winning priority group, not the highest. An unpinned
  `spark-kindling` dependency in `lake-reqs.txt` could resolve to the
  oldest wheel ever uploaded to the lake instead of the newest, with no
  warning.
- **`kindling app deploy --platform databricks` silently uploaded nothing
  on a Unity Catalog volume-only setup.** `DatabricksAPI.deploy_app`/
  `cleanup_app` only understood ABFSS; both now resolve the artifacts
  destination the same way the rest of the class does (Volumes or ABFSS)
  and upload through the shared `ArtifactStore` abstraction.
- **`kindling env update`/`kindling env bootstrap` could leave a uv
  workspace looking "in sync" while installing none of its Kindling
  packages.** Bare `uv sync` at a workspace root only installs the root's
  own dependencies; both commands now run `uv sync --all-packages`.
