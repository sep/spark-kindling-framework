# v0.14.0 — Kindling on PyPI; untracked SCD columns; surrogate keys

The first minor release since 0.13. Kindling is now installed from PyPI,
every extension's version follows Kindling's, and the cluster bootstrap checks
each extension against the runtime it is loading into. SCD entities gain
untracked columns that update in place, and entities can declare surrogate
keys that the framework computes.

Package versions:

- Runtime, CLI, SDK: **0.14.0**.
- Every extension: **0.14.0** (Databricks, SDP, Cosmos DB, Temporal,
  OpenTelemetry Azure, ADX, Databricks Auto Loader, Visualization).

## Install from PyPI

```bash
pip install 'spark-kindling[standalone]' spark-kindling-cli
```

Published to PyPI: `spark-kindling`, `spark-kindling-cli`,
`spark-kindling-sdk`, and the Databricks, SDP, Cosmos DB, Temporal and
OpenTelemetry Azure extensions. The ADX, Databricks Auto Loader and
Visualization extensions stay on GitHub Releases only. GitHub Releases still
carry every wheel, byte-identical to PyPI's.

Releases upload from CI only after every gate passes, including the cloud
system tests, through PyPI trusted publishing (no stored tokens). Release
candidates go to TestPyPI.

## Extensions follow Kindling's major.minor

An extension's major.minor now says which Kindling major.minor it works with;
its patch number counts its own fixes. All extensions are 0.14.0 in this
release and require `spark-kindling>=0.14.0,<0.15` (the Databricks extension
also requires SDP from the same line). Before, each extension kept its own
version (0.1.0 to 0.4.1); those numbers do not continue.

## The cluster bootstrap checks extensions

- **An extension built for another Kindling minor fails the bootstrap** with
  `ExtensionCompatibilityError`, naming both versions. Before, it loaded and
  could fail later in unrelated-looking ways. Extensions already installed on
  a reused cluster are checked too.
- **Installing an extension never reinstalls Kindling.** An extension's own
  Kindling requirement is checked, never installed, so pip can't replace the
  runtime the bootstrap installed with a copy from a package index. Its other
  requirements install first, keeping the runtime's packages as in 0.13.5,
  and the extension only after they succeed.

## CLI pins PyPI versions

- `kindling package init` and `kindling env add` / `env update` /
  `env bootstrap` write `==` version pins for packages on PyPI instead of
  release wheel URLs. `--source auto|pypi|github` chooses; `auto` (the
  default) uses PyPI when the release is there. GitHub-only extensions always
  pin their release wheel URL.
- `env add` brings in an extension's Kindling extension dependencies from the
  same release (e.g. SDP for the Databricks extension), and moves ones already
  declared from another release.
- `env update` resolves once, after every pin is rewritten, so moving Kindling
  and its extensions to a new minor no longer fails partway.

## SCD: untracked columns update in place

- **`scd.untracked`** lists columns that never count as a change, the
  counterpart of `scd.tracked` (declare one or the other). On an SCD2 entity a
  change only to untracked columns, or only to `scd.sequence_by`, updates the
  current version in place instead of opening a new one; a tracked change
  still closes the current version and opens a new one. On a keyed (SCD1)
  merge with `scd.untracked`, a matched row is rewritten only when another
  non-key column differs.
- **SCD2 merges take one row per business key per batch.** With
  `scd.sequence_by` the latest row wins; without it exact duplicates collapse
  and a key whose rows differ is rejected with an error naming the key.
- **SCD2 merges add new columns to the table**, as the default keyed merge
  does.
- Delta and memory providers, batch and streaming, and the Lakeflow lowering
  (`track_history_except_column_list` / `track_history_column_list`).

## Surrogate keys

Entities declare key columns with tags and Kindling computes them:

```python
tags={
    "scd.type": "2",
    "surrogate.column": "customer_sk",          # version key
    "surrogate.durable_column": "customer_dk",  # same for every version
}
```

- Strategies: `hash` (sha256 hex, the default), `uuid5`, or `custom` through
  `@SurrogateKeyGenerators.register`, which builds the key Column from a
  `KeyContext` (`kind`, `options` from `surrogate.generator.<option>` tags,
  and the standard `canonical()` / `hash()` helpers).
- Every strategy hashes one canonical string, the `v1` encoding, recorded on
  the table. Keys don't depend on column names or the session timezone, and
  NULL, empty strings and embedded separators can't collide.
- Keys are insert-only: never tracked, never updated in place, never changed
  by a close.
- Not yet lowered to SDP/Lakeflow: declaring such a pipe fails validation.
  `uuid4`, `identity` and the other planned options are rejected as not yet
  supported.

See the *Surrogate Keys* section of `docs/guide/data_entities.md`.

## Upgrading from 0.13

0. **Install the 0.14 CLI first, and run it by its full path.** The CLI that
   knows about PyPI is the 0.14 one; a 0.13 CLI still updates you to 0.14.0,
   but writes wheel-URL pins.
   ```bash
   uv tool install spark-kindling-cli
   ~/.local/bin/kindling --version     # 0.14.0
   ```
   If a project virtualenv is active, its own (0.13) `kindling` comes first on
   `PATH`, so use the full path, or deactivate the venv, for the first update.
1. **Update your project's pins:** `~/.local/bin/kindling env update --version 0.14.0`.
   This also converts URL pins to PyPI version pins, in every project of the
   repository, including packages nested under another project and pins written
   as direct references (`spark-kindling @ <url>`).
2. **Deploy the 0.14.0 extensions with the 0.14.0 runtime.** A 0.13
   extension (0.1.0 to 0.4.1) now fails the bootstrap against Kindling 0.14:
   `kindling runtime deploy --extension ...` from the same release.
3. **Settings that list extension versions** (e.g.
   `spark-kindling-ext-otel-azure>=0.4.0`) are still satisfied by 0.14.0, but
   `>=0.14.0` states the intent.
4. **`scd.tracked` changes behaviour.** Columns outside the `scd.tracked` list
   used to be ignored when they were the only change; they now update the
   current version in place. A newer `scd.sequence_by` value with no tracked
   change also updates in place (it was ignored).
5. **SCD2 batches with several rows for one key.** Without `scd.sequence_by`,
   rows for one key that differ now fail the merge with an error naming the
   key. Deduplicate upstream or declare `scd.sequence_by`.
6. **Column names starting with `__scd2_` are reserved** on SCD2 entities.
7. **`persist.before_persist` and `read.after_read` receivers chain**: each
   gets the DataFrame the previous one returned, not the original. Check
   custom receivers that assumed the original.
8. **SCD2 tables first written by 0.13.** 0.13 wrote an SCD2 entity's first
   batch with a plain write, so on Delta those rows have NULL
   `__effective_from`, `__effective_to` and `__is_current`, and later loads
   inserted their keys again. Find them with
   `SELECT count(*) FROM <table> WHERE __is_current IS NULL`, and rebuild an
   affected table from its source.

## Other fixes

- **DAG mode orders readers of an SCD2 entity's `.current` companion after
  the entity's writer**, so they no longer see the previous run's rows.
- **A Delta SCD2 snapshot no longer closes unchanged rows** whose tracked
  columns include a null.
- **The Databricks bootstrap warns when early staging falls back to the DBFS
  root** (no `kindling.temp_path` job parameter), naming the parameter to set.
- Span durations no longer go negative or inflate when the system clock is
  corrected, and streaming recovery backoff no longer follows clock
  corrections; both use a monotonic clock.
