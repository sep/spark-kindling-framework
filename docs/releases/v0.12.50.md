# v0.12.50 — Template-driven bundles; clone and extend for declarations

Two additions on top of 0.12.49: `kindling bundle build` renders a project-owned template instead of a fixed layout, and declarations gain a clone/extend mechanism.

Package versions:

- Runtime, CLI, SDK: **0.12.50**.
- Databricks extension: **0.2.0** (unchanged).
- SDP extension: **0.3.4** (unchanged).
- Cosmos DB extension: **0.2.0** (unchanged).
- Temporal extension: **0.2.7** (unchanged).

## `kindling bundle build` renders a template

The bundle is ordinary Databricks bundle YAML with Jinja placeholders. The renderer from 0.12.49 is now the built-in default template and produces byte-identical output; `kindling bundle template init` copies it into a project so resource keys, display names, tags, per-pipeline permissions, clusters or any other bundle field are owned in YAML the project writes, with nothing for Kindling to model or lag behind on. A team migrating from a hand-authored bundle turns that bundle into the template by replacing each pipeline's configuration block with `kindling.configuration(<app>, ...)` and the wheel list with `{{ dependencies }}`, so pipeline identity is preserved by construction.

The generator supplies only what it uniquely knows: `apps[<name>].settings`, merged by convention, and `kindling.configuration(app, pipes=None, extra=None)`, which returns a pipeline's complete configuration map including the inline `kindling.lakeflow.settings_json` and a `kindling.lakeflow.config_keys` naming every emitted key a restricted runtime must point-look-up. Rendered resources are parsed back: a pipeline whose configuration did not come from the helper, whose `settings_json` is not the selected app's merged settings, or whose `config_keys` is incomplete fails the build. Files ending in `.j2` render (a `__pipeline__` name renders once per pipeline); other files are copied verbatim and validated the same way. Renders stage into a sibling directory and replace the previous output only on success, template output may not collide with staged wheels or the manifest, `--app` may be omitted to build every app under the app roots, `template init` refuses the project root, and the manifest records the template files' hashes with per-app settings sources under `apps`.

## Clone and extend for entities and pipes

One mechanism, a *derivation* (`docs/proposals/declaration_derivations.md`). `DataEntities.clone(id, from_entity=..., ...)` and `DataPipes.clone(id, from_pipe=..., ...)` declare a new id from another declaration used as a template; a clone implies nothing about data. `DataEntities.extend(id, ...)` and `DataPipes.extend(id, ...)` change a declaration in place. Changes are additive and stack last-in-wins, like config overlays: `tags` (later value wins per key), `add_columns` (names accumulate; the same name with a different type is an error, because retyping is a migration), `add_partition_columns`, `add_cluster_columns`, `add_inputs`, and a pipe `transform(previous_output, **added_inputs)` that wraps the execute with the last registered outermost. The original execute receives exactly its own inputs; the result is still one pipe with one execute, so the runner, streaming and the declarative engine see nothing new, and a cloned pipe keeps its own watermark state.

Derivations resolve when their source is registered, in any import order. A target whose source never appears is reported by `pending_derivations()`, warned about after the bootstrap overlay pass, and raises on lookup instead of reading as an unknown id. A clone copies the source's raw declaration plus its extensions, never the config-overlaid result; overlays then target the clone by its own id. The YAML form uses `clone_of`, `add_columns` (`{name, type}` with atomic Spark SQL type names, `decimal(p,s)` or `array<type>`, parsed without a Spark session) and `add_inputs` on exact ids under `dataentities:`/`datapipes:`, re-applied wholesale on every overlay pass. `kindling entity show` prints the derivation chain.
