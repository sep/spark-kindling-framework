## A warning when configuration silently clears `merge_columns`

`merge_columns` is an ordinary overridable `EntityMetadata` field, and list values **replace** rather than merge under the `dataentities:` / `dataentities-bytag:` overlay. A rule that carries a `merge_columns` key — even incidentally, such as an empty list on a broad tag rule — therefore drops a validly declared merge key with no other signal, and the next thing the user sees is `kindling app validate` failing with "delta entity missing merge_columns" as if the framework had ignored correct code. The overlay now logs the actual cause at override time, naming the entity, the declared columns and what replaced them. The override still applies exactly as before; it just stops being silent (#294).

## Order-independent Delta sessions in the test suite

Moving Delta-backed test modules from `tests/unit` into `tests/integration` (#296) surfaced a latent fragility in the shared test helper: `get_standalone_spark_session` promised a Delta-configured session "regardless of test order", but it ended in `getOrCreate()`, and Spark's JVM is a process-wide singleton whose `spark.jars.packages` is honoured only at gateway launch. When an earlier module had already launched the JVM without Delta jars, the helper handed back that jar-less JVM and Delta failed with `Cannot find catalog plugin class … DeltaCatalog`. Neither the CI image nor the devcontainer ships Delta on Spark's default classpath, so this was purely a matter of which module launched the JVM first; `main`'s Integration Tests job was red from the #296 merge until this fix.

Getting this right took four rounds, each of which taught something worth recording:

- **The decision is about the JVM, not the session.** Whether Delta is available is decided by how the JVM was launched, read from the spark-submit command line the py4j gateway was started with (`gateway.proc.args`). A SQL conf value is not evidence (`getOrCreate()` copies builder options onto an existing session), a py4j `Class.forName` probe is a false negative (it resolves through the gateway's classloader, not Spark's), and a SparkContext's `listJars()` goes quiet for a context created after a `stop()` in the same JVM even though the jars are still on its classpath. A Delta-launched JVM is reused untouched whether or not a session is active; only a jar-less JVM, or a dead gateway, is relaunched.
- **`gateway.shutdown()` does not end the JVM.** PySpark launches it with a stdin pipe and the Java side exits on EOF of that pipe, which only happens when the Python process dies. The six integration modules that relaunched per module had each been leaving a ~1 GB orphan behind; under four xdist workers the CI runner was OOM-killed (exit 137) the moment the relaunch started happening more often. The shared teardown now reaps the launcher process.
- **The orphans were load-bearing.** Once the reap was real, killing a JVM took down everything bound to it — wider-scoped fixtures, PySpark UDF objects that cache their Java counterpart, kindling's global session — which the orphaned JVM had silently kept serving. Hence the rule above: never kill a Delta-launched JVM. Relatedly, conftest's `spark_session` fixture is module-scoped instead of session-scoped, because other modules' `getOrCreate()` hands back that very session and their teardown `stop()`s it; per module it is recreated on the live JVM.
- The lifecycle is pinned by seventeen unit tests with fake gateways, launcher processes and sessions (no JVM), so none of the above can regress silently while the integration suite happens to pass. Also found on the way: `tests/test_kda_packaging.py` returned `False` on failure, which pytest counts as a pass — it asserts now.
- The six private `_teardown_existing_spark_jvm` copies are gone; `get_standalone_spark_session`, `get_local_spark_session` (the conftest fixture's path) and the Azure helper all run the same preflight; an externally started gateway is never torn down (#297).

## CI can now see cross-suite state leaks

The unit and integration CI jobs each run their suite in a fresh interpreter, so state that leaks from one suite into another is structurally invisible to them. Running every local suite in **one** process — integration before unit, in collection order — is what exposed the eighteen unit failures fixed in 0.12.45 (a module reload splitting a class identity; an environment variable a fixture never restored). A new job, **Full Suite (single process)** (`poe test-all-ci`), runs that arrangement on every push and pull request so the next such leak is caught when it is introduced rather than months later. Its very first run caught the Delta-session regression above. Cloud system tests are skipped there; they keep their own lane, and `tests/local-project` remains a separate fixture project run by `poe test-local` (#297).

Alongside it: `poe test` now passes `--skip-system`, because system tests are not auto-skipped without workspace credentials and a bare run on a developer machine failed 27 cloud tests as environment noise; the lake-wheel BFS system test's failure message now quotes the `[BFS] Not found in lake` lines from the job log, so a missing top-level dependency (wheels absent from the listed directory) is no longer reported as a transitive-resolution failure — the misdirection that cost the 0.12.45 diagnosis; and the release-process guide documents that Copilot reviews only the first head it sees and must be asked to re-review fix-up commits before a fast-track merge.

## Spark-dependent tests moved out of the unit suite

Tests that need a JVM-backed `SparkSession` no longer live in `tests/unit`: four whole modules, the Event Hubs preprocessing tests (real Catalyst expressions and the AMQP header-decoding UDF over real DataFrames), four temporal engine tests, and the two watermark-span tests whose `col(...)` predicate needs a live `SparkContext` all moved to `tests/integration`, with shared Event Hubs helpers extracted. `poe test-unit` starts no JVM for any of them (#296). The real-Spark SDP dataset test also gained an isolated injector and physical-name resolution coverage across all three tag shapes the name mapper supports — the live-Spark counterpart of the resolver fix in 0.12.44 (#295).

## Proposal: Cosmos DB change-feed streaming and throughput controls

`docs/proposals/cosmos_streaming_and_throughput_controls.md` proposes change-feed streaming reads for the Cosmos extension plus config-first throughput controls. Five review corrections are folded in: the declarative engine requires `DeclarableStreamingSource` alongside `StreamableEntityProvider`; the change feed is a distinct data source (`cosmos.oltp.changeFeed`) from the OLTP one; change-feed defaults must apply before the generic `provider.option.*` passthrough so the passthrough keeps precedence; `target_threshold` and `target_throughput` are alternatives and are now rejected together; and Parquet already implements `StreamableEntityProvider` (#293).
