# v0.12.47 — Provider config is `provider.*` only

A small release with one behavior change on the entity-provider base class, the completion of a deprecation begun in 0.12.35, and two development-environment items.

Package versions:

- Runtime, CLI, SDK: **0.12.47**.
- Databricks extension: **0.1.14** (unchanged since 0.12.44).
- SDP extension: **0.3.4** (unchanged since 0.12.44).
- Temporal extension: **0.2.7** (unchanged since 0.12.43).

## Generic entity tags no longer leak into connector options

`BaseEntityProvider._get_provider_config()` used to copy every unprefixed entity tag into the provider configuration alongside the prefix-stripped `provider.*` tags. That was documented and tested as intentional, and it was harmless until tags gained framework-level meanings: the SDP declaration engine reads a `comment` tag for the Unity Catalog table comment (#165). `CSVEntityProvider.read_entity` forwards any config key it does not name to `spark.read.format("csv").options(**...)`, so an entity declared as

```python
tags={"provider_type": "csv", "comment": "Source stream of raw device telemetry Kafka records."}
```

handed that sentence to Spark as the CSV `comment` option, which must be a single character, and the read failed with `comment cannot be more than one character`.

`_get_provider_config()` now returns `provider.*` tags only, prefix stripped and type-converted exactly as before. Generic tags (`provider_type`, `layer`, `stage`, `comment`, `sdp.*`, application tags) are excluded from the provider-config mapping and therefore from any connector options built from it. The exclusion is from that mapping only: providers still receive the full `EntityMetadata`, and the registry still selects a provider by `provider_type`. A provider that needs a generic tag reads `entity_metadata.tags` directly. Applications keep their UC `comment` tags as they are; no `provider.comment` workaround is needed.

This is a contract change on a base class that third-party providers subclass. A provider that read a bare (unprefixed) tag through `_get_provider_config` must read it from `entity_metadata.tags`, or the application must declare it as `provider.<key>`. Every in-repo provider and every documented provider tag already used the prefix; a survey of the providers that forward config to Spark found CSV reads to be the only path that could leak (Event Hubs builds explicit option dicts, Delta forwards caller-supplied options, Memory/Parquet/ADX read named keys).

Coverage: the Delta test that asserted inclusion now asserts exclusion; CSV unit tests check the provider-config mapping and the reader's option calls; a CSV integration test loads a file whose entity carries a multi-character `comment` through a real local Spark session; and the view/CSV roundtrip system test now gives its entity `comment`, `layer` and `sdp.*` tags and reads back through `CSVEntityProvider.read_entity()` on Fabric, Synapse and Databricks (#301).

## `kindling.lakeflow.config_files` alias removed

The comma-separated Lakeflow compatibility alias that 0.12.35 (#281) deprecated in favour of `spark.kindling.bootstrap.config_files` is gone. The key is now ignored: not bridged into bootstrap `config_files`, not warned about. A pipeline that still sets it loads no settings files from it and must move the paths to `spark.kindling.bootstrap.config_files` as a JSON array string (or a bare string for one file). `LakeflowConfigSourceError`, the never-raised stub kept for the same cycle, is removed from `kindling_ext_databricks` with it. Removed ahead of the 0.13.0 eligibility the deprecation notice named, by decision on #298 (#299).

## Devcontainer: docker-init as PID 1

`sleep infinity` as PID 1 never calls `wait()`, so every orphaned process in the devcontainer became a permanently unreapable zombie holding a cgroup PID (19.7k in 24 hours under agent load). The compose service now sets `init: true`, so the daemon runs tini as PID 1; no image change (#300).

## Proposal: Databricks bundle build and deployment

`docs/proposals/databricks_bundle_deployment.md` proposes having the Kindling CLI materialize a disposable Databricks Asset Bundle from an existing domain project, reusing its built wheels, with the Databricks CLI validating, deploying and running it. Bundle artifacts are generated output or existing project assets; developers do not maintain a second set of bundle YAML. Lakeflow pipelines first; KDA and durable-runner deployment keep their own path. Status: proposed, not implemented (#300).

Validation: full validated release lane — unit, integration, quality, security, KDA, wheel builds, the single-process suite and the Fabric, Synapse and Databricks system tests.

Includes #299, #300, #301.
