# v0.13.5 — Spark 4 fixes, extension installs that keep the runtime's packages

A patch release. A new Spark 4 test lane found four bugs on Spark 4.0 (Databricks Runtime 17.x), and the Databricks Azure Monitor extension test found a fifth. This release fixes all five and changes how extensions install on a cluster.

Package versions:

- Runtime, CLI, SDK: **0.13.5**.
- OpenTelemetry Azure extension: **0.4.1**.
- Other extensions: unchanged (Temporal 0.2.8, Databricks 0.2.0, Databricks Auto Loader 0.1.0, SDP 0.3.4, Cosmos DB 0.2.0, ADX 0.1.0, Visualization 0.1.0).

## Extension installs keep the runtime's packages

The cluster bootstrap used to install an extension with `pip install --ignore-installed --upgrade --upgrade-strategy eager`, which put the newest version of every dependency over the runtime's own copy. On Databricks Runtime 17.3, the OpenTelemetry Azure extension replaced OpenTelemetry, azure-core, azure-identity, msal and more. On Fabric it replaced azure-core.

Extensions now install without those flags. Each runtime's key packages (azure-core, azure-identity, msal, OpenTelemetry, typing-extensions, numpy, pandas, pyarrow, protobuf, pyspark, py4j) are pinned at their installed versions, so pip picks the highest extension dependency versions that work with them. When there's no other way, the bootstrap falls back:
- **pip can't replace an installed package** (installed by conda or distutils): the install is retried with `--ignore-installed`, and the key packages stay pinned.
- **The requirements can't be met with the key packages pinned:** the install is retried without the pins.

Every installed package an install changes is logged as a warning.

The OpenTelemetry Azure extension now accepts azure-monitor-opentelemetry 1.6 through 1.8, so Synapse keeps the 1.8.2 it ships. `poe check-extension-runtimes` checks every extension against the packages Databricks 17.3, Fabric 1.3 and Synapse 3.5 ship.

## The Azure Monitor extension takes effect for every logger lookup

The bootstrap resolves Kindling's default logger provider before it loads extensions, and the DI container kept handing out that cached instance after the Azure Monitor extension rebound it. So `get_kindling_service(PythonLoggerProvider)` returned the default provider, and those logs never reached Azure Monitor. Rebinding now replaces the cached instance too. Loggers created before the extension loaded, such as the bootstrap's own, keep the default provider.

## Spark 4 fixes

- **YAML `add_columns` types parse on Spark 4.** They used a private PySpark name that Spark 4.0 removed, so every typed column failed with `ImportError`.
- **Event Hubs `preprocess: kafka` tolerates invalid UTF-8.** Spark 4 makes `decode()` fail the query on malformed bytes; Kindling now replaces them with U+FFFD, as Spark 3 did.
- **Event Hubs `amqp_headers` works over Spark Connect** (Databricks standard/shared access mode). The header UDF was built when Kindling was imported, before a Connect session existed.
- **The memory provider no longer reports a missing entity as existing over Spark Connect**, where `spark.table()` doesn't fail until the data is read.

## Other changes

- **Spark 4 test lane.** `poe test-spark4 --mode classic|connect` runs the unit and integration suites on Spark 4.0, classic or over Spark Connect. CI runs both for runtime changes.
- **The lock tests the highest versions the dependency ranges allow**, for packages no supported runtime ships.
